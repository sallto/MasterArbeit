This chapter describes how we extend the TPDE framework to support better register allocation choices, maintaining a single-pass code generation.

First we perform a lifetime analysis that calculates the distance to the next use of a value at each point.
Then a spilling pass marks registers to be spilled at points with high register pressure (\regpressure{}), spilling the furthest next-use ($x$ at $B$, and $y$ at $L$). These values are then spilled after their definition. 
Additionally, we calculate a minimal register set for loop headers, that contains as many loop values as possible, while spilling non-loop values ($y$ at the end of $B$).

During code generation we insert reloads as necessary to encode instructions. When encountering constrained instructions such as \texttt{add} on \texttt{x86-64}, we attempt to repair the register state by moving values to different registers. This prevents the values from being lost due to instruction constraints.
At branches, we insert connecting code to ensure that the register state matches the target block, and the calculated loop header state, if we branch to a loop header.

\section{Liveness with Next-Use Distance}

As described in \autoref{sec:tpde}, the existing liveness analysis in TPDE operates at the basic block level and does not account for lifetime holes.

This is insufficient for an effective register allocation as it creates too many interferences between variables, that are not actually present in the original program.

To address the issue, we introduce a precise liveness analysis, that also calculates the next-use distance at each point in the program.

To accomplish this, we adapt the approach by \textcite{fast-liveness}.  %todo fix this citation

We define the next-use as the number of instructions between \emph{start of the current block} and the next use of the variable. Next-uses are therefore always strictly increasing within a block. The next-use distance can easily be calculated using the index of the current instruction and the next use.

\subsection{Data Structures}

We chose to store this information as a sorted (by construction) list of next-uses for each variable and block. Definitions are marked by having their highest bit set. Therefore, a value is defined in a block if its first next-use entry has the highest bit set (and is not dead). Dead values have a next-use of \texttt{u32::max} or no entry if the value is neither live-in nor defined in the block. A value is live-out if its last entry is not \texttt{u32::max}. 

For example, the following array describes a value that is defined in the second instruction of the block and used as an operand in the third instruction, after which it is dead.

\begin{center}
    \begin{tabular}{|c|c|c|}
        \hline
        0 & 1 & 2 \\
        \hline
        \texttt{(\texttt{1<<31}) |  1} & 2 & \texttt{u32::max} \\
        \hline
    \end{tabular}
\end{center}

Additionally, we apply a loop exit penalty to live-out distances if the successor is part of the same loop. This penalty is simply a large number added to the distance and accounts for the frequency with which loops are executed, according to our regularity assumptions  (see \autoref{sec:tpde}).  This encourages the later spilling pass to avoid spilling loop variables ~\cite{hack-spilling}.

Overall, this allows us to find the next use of a value in logarithmic time relative to the number of uses in a basic block. As well as checking live-in, live-out and whether it was defined in the block in constant time. Additionally, checking whether a value is used in a loop takes constant time, as we assume that all other uses are below the chosen loop exit penalty.

\subsection{Partial Liveness}

First we calculate the partial liveness for each block by traversing the control flow graph (CFG) in post-order, skipping loop edges. 
We then process the instructions for each block in forward order while tracking the current instruction index and noting the definitions and uses of each variable.

To find the live-out distances, we iterate over the direct successors, while skipping loop edges and taking the minimum next-use from the successors. As we traverse the CFG in post order, the non-loop successor blocks are already processed.

Note that values used only in a $\phi$ definition are not considered live-in, but we will consider them live-out at their predecessor blocks with a use at the zeroth instruction of the successor.


\subsection{Liveness Propagation}

To propagate the liveness information through the program, we calculate a loop forest as described by \autocite{fast-liveness},  implemented using the existing TPDE loop analysis.


Liveness is propagated, by marking live-in values from a loop header as live throughout all child loops (the children of the loop header in the loop forest). This corresponds to adding a single next-use entry for each value in the children of the loop header.
The next-use entry is larger than the block size indicating that the value is both live-in and live-out, but is neither used nor defined within the block.

Whenever a value is propagated to a different loop (including $L_0$), we add the loop exit penalty to the next-use entry.

For large functions, this can lead to many live-through values, which can be problematic as our original data structure may result in up to one allocation per entry created. Instead, we track the live-through values separately in a vector, which is later sorted by the index of the value and its next-use entry. This approach still allows for quick access (in logarithmic time relative to the number of live-through values in the block) while reducing the number of allocations to one per block.

\section{Spilling}

The primary purpose of the spilling pass is to ensure that the register pressure is less than the number of registers $k$. Typically, a spilling pass inserts spills and loads into the IR. For the SSA form, $\phi$ nodes must also be inserted, as the reloaded value must be distinct from the original value in order to remain in SSA form.

However, since we don't modify the IR anywhere, we can save spills and reloads as metadata and insert them during code generation.

\subsection{Representing Spills and Reloads}

Since we can't modify the existing IR, it is not possible to insert the calculated spills and reloads. Specifically, we would need to check with each instruction whether a reload or spill needs to be generated.

This would require a lot of bookkeeping. Instead, we approximate the spill and reload locations. We avoid storing reloads, except for loop headers and will insert a reload if necessary during code generation.

For spills, we only store the information about which values should be spilled at any point in the program. Then during code generation we insert the spill immediately after the value definition. This simplifies analysis, as we don't need to track which vales where spilled in which branches, to prevent values from being lost or spilled unnecessarily again. During code generation we only need to check a single bit in a bitset for the results, reducing the overhead of the spilling pass.

This approximation of spills does not result in the optimal solution in all cases, especially around blocks with very different execution frequencies (see \autoref{fig:bad_case_spill}). This is particularly relevant for loops, which we assume to execute frequently.

\subsection{Calculating Spills}
\label{sec:spill_calculation}

We use a simplified \texttt{MIN} algorithm based on the work of \citeauthor{hack-spilling}~\cite{hack-spilling}. 

We simulate the working register set $W$ during each block by limiting its size to $k$ registers. For values that are live but need to be removed from $W$, we mark them as spilled.
Values with multiple parts, like 128-bit integers, always need to be fully in $W$ or fully spilled.

We calculate which values to spill according to the next-use distance: once before the instruction to ensure space for the operands, and once after for the results.

At this stage, we do not consider any instruction irregularities, except for calls. Calls are handled by adding an implicit result for each volatile register. Additionally, we mark values that are in $W$ after a call and that will be used in the next five instructions. Such values are good candidates for non-volatile registers.
All other irregularities are ignored (and are not known to TPDE at this stage).


\begin{algorithm}
\caption{The MIN algorithm}
\centering
\begin{minipage}[t]{0.4\linewidth}
\begin{algorithmic}[0]
\Function{limit}{$W, \textit{insn}, cap$}
    \State sortByNextUse$(W, \textit{insn})$
    \For{$v \in W[cap\!:\!-1]$}
        \If{$\mathrm{nextUse}(v) \neq \infty$}
            \State mark $v$ as spilled
        \EndIf
    \EndFor
    \State $W \gets W[0\!:\!cap]$
\EndFunction
\end{algorithmic}
\end{minipage}
\hfill
\begin{minipage}[t]{0.57\linewidth}
\begin{algorithmic}[0]
\Function{minAlgorithm}{$\textit{block}, W$}
    \For{$\textit{insn} \in \textit{block.instr}$}
        \State $W \gets W \cup \textit{insn.operands}$
        \State limit$(W, \textit{insn}, k)$
        \State limit$(W, \textit{insn.next}, k - |\textit{insn.results}|)$
        \State $W \gets W \cup \{\textit{insn.results}\}$
    \EndFor
\EndFunction
\end{algorithmic}
\end{minipage}

\caption{Simplified \texttt{MIN} algorithm for a single basic block~\cite{hack-spilling}. }

\end{algorithm}

We initialize $W$ with the function arguments. Then for every each subsequent block, we initialize $W$ with the intersection of all incoming values from predecessors. Since we don't insert reloads at this stage, the initialization is not critical, unless the current block is a loop header.

For loop headers, we initialize $W$ to contain only the variables used in the loop, restricting it to $k-p$ registers, where $p$ is the approximate maximum register pressure in the loop. This pressure $p$ is calculated during the liveness analysis and is simply the maximum number of live variables in any of the loop blocks. 
This tries to ensure that loop iterations can be executed without spilling. 
However, since  our register pressure $p$ is only an approximation, we conservatively evict all values that are not used in the loop.

\section{Register Allocation during Code Generation}

Having completed the previous stages, we have now reached the code generation stage of TPDE. Therefore, any generated instruction cannot be undone, as they are encoded immediately. 
The focus of this stage is avoiding additional spills, other than those previously calculated, and handles connecting basic blocks together including $\phi$ nodes.

\subsection{Register Choice in a Basic Block}
\subsubsection{Register Choice for Unconstrained Instructions}
When a value requests a register, we select one from the currently unused registers in round-robin fashion. Volatile registers are preferred unless the value has previously been marked as non-volatile (see section~\ref{sec:spill_calculation}).
The chosen register is then noted as the preferred register for this value. Future reloads of this value will try to use the same register if possible, in order to minimize connecting instructions~\cite{treescan}.

If there are no free registers, a value must be spilled. To do this, we select values with the largest next-use distance. These values are usually already marked as spilled and therefore do not generate a new spill.
\subsubsection{Register Choice for Constrained Instructions}

For constrained instruction, the associated compilation function (see~\autoref{lst:example-div}) will either use a scratch register or request a specific register. Scratch registers are handled like normal values except that they cannot be spilled and no preferred register is stored as they are temporary. If a specific register is requested, and the register is currently in use, we move the occupying value into a free register if possible, thereby repairing the assignment instead of spilling. If no register is available, the occupying value is spilled,  since the previously calculated spill information is not correct around constrained instructions. 

As requests are processed value by value it is possible, that we miss shuffling opportunities between operands.

For example assume we want to compile an unsigned 64-bit division on \texttt{x86-64}, which requires the dividend to be in \texttt{rax} and \texttt{rdx} to be zero. If we have the dividend $x$ in \texttt{rdx} and the divisor $y$ in \texttt{rax}, and all other registers are occupied. We will first spill $y$ to free up \texttt{rdx}, then spill $x$ to free up \texttt{rax}, and finally we need to spill an arbitrary register for $x$.

This could be avoided by first getting the arbitrary register for $x$, then moving $y$ from \texttt{rax} to the new register, and finally moving $x$ into \texttt{rax}. 

Although this scenario is possible, it is unlikely to occur as long as most instructions are unconstrained.
Values would also need to be in specific registers by chance, and there would need to be high register pressure at this point. 

However, such situations may be problematic for calls, as all arguments have a specific location, and they occur frequently in programs. Therefore, we handle calls separately.

\subsubsection{Register allocation for calls}
For calls, all operands must be located either in a specific stack or in a specific register.

We first collect all operands and their target locations and spill all volatile registers. 

In a second pass we first move all stack operands to their location, which frees up more registers. 
Finally, we use a parallel move algorithm~\cite{par-move}, which uses the free registers as temporaries in order to swap values between registers and resolve any dependency cycles.

\subsection{Connecting Basic Blocks}

At the end of each block we connect it to its successors. If the successor has only one predecessor, we can simply use the current register without any additional moves.   For blocks with multiple predecessors, we use the register state of the first predecessor generated.  If the current register state does not match the target state, we generate a parallel move to resolve the differences. To ensure this is possible, we require one register per bank to be free in branch regions. This enables us to use parallel moves to resolve any register conflicts. We minimize the number of connecting moves using the preferred register mechanism.

If a successor contains $\phi$ nodes, we try to allocate them to a register and move their incoming value to this register, this is done in the same parallel move. This can also handle all cycles or swaps between $\phi$ nodes, provided they are in registers. If the $\phi$ nodes are not in registers and conflict, we try to use the free register as an intermediate; otherwise, we need to allocate an additional stack slot to resolve the conflict. 

As it is not possible to undo any action taken during the connection step, all jumps currently need to be split. However, it would be possible to pre-calculate whether any moves, spills or reloads are necessary, and then decide whether a jump must be split.

\subsubsection{Loop Headers}

As previously described, we consider loop headers to be especially important and have therefore precalculated the register state during the spilling phase. This is used when connecting to a loop header. All non-loop values are spilled, and the missing values are reloaded into registers, to ensure registers match the precalculated state.
