\chapter{Evaluation}\label{chapter:evaluation}
\section{Correctness}
We verify the correctness of our implementation using the LLVM test suite as well as the SPEC CPU2017 integer benchmarks. Except for a few test cases that rely on unsupported instructions, all tests pass successfully on both \texttt{AArch64} and \texttt{x86-64}. We consider this to be a strong indicator of the correctness of our implementation.

\section{Setup}
We evaluate the performance of our implementation by measuring the back-end
compile-time and the run time performance of LLVM-IR generated by LLVM using the optimized (\texttt{-O1}) frontend pipeline.

We compare our implementation \footnote{Commit ff5f13a5} against
 the original version of TPDE\footnote{Commit 930ff2b} and against both the LLVM-O0 and LLVM-O1 back-ends, the former two focusing on compile-time, while the latter is an optimizing back-end. 

As benchmark programs, we use the SPEC CPU2017 integer benchmarks on \texttt{x86-64} and \texttt{AArch64}.
Our \texttt{x86-64} machine is an AMD Ryzen 5 5600X with 32 GiB of RAM running Linux 6.18.12; Our
AArch64 machine is an Apple M1 with 16 GiB of memory, using only the four performance cores,
running Asahi Linux 6.17.12. We use Clang/LLVM version 20.1.8.

All runtime performance measurements are performed twice, with the average time being reported. Compile times are calculated from 5 runs, discarding the slowest and fastest runs. We then report the average of the remaining three runs.

As both architectures show similar results, we will refer to the \texttt{x86-64} version, unless otherwise noted.

First, we compare our solution with the LLVM back-ends, as well the original TPDE on optimized IR. 
The produced IR uses $\phi$ nodes and is in SSA form with relatively long live ranges, making it a good candidate for comparison.

\autoref{fig:spec_runtime_speedup} shows an overall improvement in the runtime performance of $24\%$ ($0.573\times$ vs. $0.710\times$) for our work compared to llvm-O0 backend, and a improvement of $15\%$ ($0.618\times$ vs. $0.710\times$) for our work compared to the original TPDE. Compared to llvm-O1 backend, which has a better instruction selection, register allocation and performs additional optimization passes on the IR, our work is $30\%$ slower. 

However, the performance improvement is not uniform 
 across benchmarks, with some showing no improvement when compared to TPDE.
We will use \texttt{600.perl} as a representative example to illustrate issues that arise when using optimized IR as the basis for register allocation.

\subsubsection{Suboptimal structures resulting from LLVM-O1 pipeline}

The clang and LLVM-O1 frontend pipelines perform multiple transformations, but the resulting IR is not designed for direct use without further transformations. For example the loop invariant code motion pass (LICM) moves instructions outside of loops wherever possible. This results in many pointer offsets (\texttt{getelementptr}) to be moved to the beginning of functions. Additionally, there is no deduplication pass for values after LICM, which resulting in numerous duplicate values  for the same pointer offset. For the function \texttt{S\_regmatch} from \texttt{600.perl}, which is its bottleneck, we find at least $7000$ usages of such values.

\begin{lstlisting}[float,frame=none,caption={Excerpt from the function \texttt{S\_regmatch} from \texttt{600.perl} (simplified for readability). Showing structures resulting from loop invariant code motion.}, label={lst:example-licm}, language=llvm,captionpos=b,escapeinside={(*@}{@*)}]
  early_block:
  %strbeg2306 = getelementptr i8, ptr %reginfo, i64 8
  %strbeg1235 = getelementptr i8, ptr %reginfo, i64 8
  %strend = getelementptr i8, ptr %reginfo, i64 16
  %not = icmp eq ptr %cur_eval.1.ph, null
  (*@\centerline{\raisebox{-4pt}[1pt][1pt]{$\vdots$}}@*)
  inner_blocks:
  %strbegval = load ptr, ptr %strbeg1235
  %strendval = load ptr, ptr %strend
  (*@\centerline{\raisebox{-4pt}[1pt][1pt]{$\vdots$}}@*)
  br i1 %not, ...
\end{lstlisting}

This is highly problematic for our implementation as each of these values is compiled at an early block of the function and then spilled as they are not used for most of the program. Then, on every load, the address needs to be loaded from (where the same value is duplicated in many slots) and only then can the actual value be loaded. On \texttt{AArch64}  large number of these values  also results in an additional instruction for calculating the stack slot address, as the offset is too large to be encoded as an immediate value in the instruction, due to the thousands of values on the stack.

A better solution would be to keep the base pointer in a register, as it is used frequently throughout the program. Then compute the offsets on demand, which are typically small enough to be encoded as immediate values in the instruction\footnote{On \texttt{AArch64} only small offsets can be encoded, but this also applies to the stack pointer, so keeping a base pointer in register is the better option.}. This is the approach taken by the LLVM-O1 back-end, which results in much better performance. 

Similarly, some comparisons are moved far from the branches that actually use them, which means we can no longer fuse the comparison with the branch instruction.

Consequently, most of the code generated by both TPDE and our implementation consists of spills, reloads, and connecting code. It may be possible to fix this for pointer offsets by internally tracking the base pointer, but this would require significant changes to the implementation. For other values, however, this is not realistically resolvable without reimplementing an optimization pipeline, which would remove TPDE's main advantage: its low number of passes.



Another pattern is illustrated in \autoref{lst:example-smallcond}, where we see many small basic blocks, each containing a single comparison and a branch.
LLVM-O1 combines these small blocks into a single label with multiple jumps. Our implementation generates them all separately and also generates connecting code to the merge block every time resulting in many duplicated spills, reloads and moves. 

\begin{lstlisting}[float,frame=none,caption={Excerpt from the function \texttt{S\_regmatch} from perlbench. Showing very small basic blocks, chained together to utilize phi nodes.}, label={lst:example-smallcond}, language=llvm,captionpos=b,escapeinside={(*@}{@*)}]
  cond.false409:
  %cmp410 = icmp ult i64 %x, 67108864,
  br i1 %cmp410, label %cond.end431, label %cond.false413
  cond.false413:
  %cmp414 = icmp ult i64 %x, 2147483648,
  br i1 %cmp414, label %cond.end431, label %cond.false417
    (*@\centerline{\raisebox{-4pt}[1pt][1pt]{$\vdots$}}@*)
  cond.end431:
  %y = phi i64 [ 0, %cond.false409 ], [ 1, %cond.false413 ], ...

\end{lstlisting}

Such patterns are found on the hot functions of $600.perl$, $620.omnetpp$ and $623.xalanc$, which are  benchmarks showing little performance improvement for our version.

\subsubsection{Other Limitations}

In addition to the aforementioned issues, there are some other limitations of our implementation that may  contribute to the performance gap to llvm-O1. Since we lack a coalescing analysis, we generally need separate registers for the phi and its next-incoming, resulting in higher register pressure. This leads to poorer instruction selection on \texttt{x86-64}, as we cannot use the add and sub instructions, as these overwrite their source operands. We also don't perform any instruction scheduling, which would reduce register pressure (see \texttt{rax} and \texttt{r9} in the left snippet of \autoref{fig:asm}). Additionally, our implementation currently splits all conditional branches, leading to more jumps and a worse code layout. 

Since we spill all non-loop variables when entering a loop header, unnecessary spills can result if the loop has low register pressure (see \autoref{fig:asm}). Since we don't know the actual register pressure at the spill stage it is difficult to design a better heuristic for this issue, as an additional spill/reload in the loop would be more expensive than the unncessary spills outside the loop.

When comparing sizes of the \texttt{.text} segment of the generated binaries, we see an increase of $12\%$ for our implementation compared to TPDE (geomean $2.05\times$ vs $1.83\times$), both being around twice the size of LLVM-O1. We usually expect better register allocation to lead to a smaller code size, but in this case, splitting jumps and matching register sets for all branches leads to an increase in code size. 


On \text{AArch64} we see a worse performance when compared to LLVM-O0, which is due to its usage of \texttt{GlobalISel} for the unoptimized pipeline as opposed to \texttt{FastISel}.

The primary way to avoid this code size increase would be to optimize scenarios similar to \autoref{lst:example-smallcond}, by generating most of the connecting code at the beginning of the merge block instead of at each of its predecessors. 

Matching the code size of LLVM-O1 is not possible due to the superior instruction selection and additional optimizations performed by LLVM-O1 (see \autoref{fig:asm}).
\section{Discussion}

Our results show, that we were able to achieve a moderate improvement in runtime performance compared to the original TPDE, while still remaining significantly faster than LLVM-O0. However, there is still a significant gap to LLVM-O1, which is difficult to close without more elaborate analyses. Especially in the worst performing benchmarks, where we see no improvement while incurring a large compile-time penalty.
Some compile-time gap to TPDE may be closed by optimizing the implementation, specifically around minimizing the number of allocations.

Nevertheless, our implementation is a new pareto-optimum for compiling optimized IR, as it is significantly faster than LLVM-O1 while still providing a runtime improvement compared to both TPDE and LLVM-O0. Additionally, our implementation is independent of the IR, so it may be used as a back-end for other IRs, where problems such as the LICM may be avoided.


\section{Unoptimized IR}

When running the same benchmarks using unoptimized (-O0) IR, we see no runtime performance improvement between TPDE and our work, while still incurring a similar compile time penalty of $4$ times (geomean $4.90\times$ vs. $19.34\times$). 
As our analyses were designed for IR with long live ranges and phi nodes, applying them to unoptimized IR results in suboptimal performance.

\begin{lstlisting}[float,frame=none,caption={Example of IR generated by LLVM-O0, using stack slots for loop variables, that would be $\phi$ nodes otherwise. }, label={lst:example-unopt}, language=llvm,captionpos=b,escapeinside={(*@}{@*)}]
  %i = alloca i32, align 4
  %j = alloca i32, align 4
  (*@\centerline{\raisebox{-4pt}[1pt][1pt]{$\vdots$}}@*)
  %58 = load i32, ptr %j, align 4
  %59 = load i32, ptr %k, align 4
  %cmp = icmp slt i32 %58, %59
  br i1 %cmp, label %for.body, label %for.end
\end{lstlisting}

The IR generated by LLVM-O0, uses stack slots using \texttt{alloca} instead of $\phi$ nodes and loads and stores to them frequently. Therefore, most values have a short life range and functions rarely have a high register pressure, which prevents our approach from improving the code generation. Additionally, values with exactly one use represent the worst case for our liveness analysis, as they still generate an allocation, which is not amortized by multiple uses.
